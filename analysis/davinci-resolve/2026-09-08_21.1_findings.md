# DaVinci Resolve 21.1 — macOS installer findings

- **Package:** `Install Resolve 21.1.pkg` (from `DaVinci_Resolve_21.1_Mac.zip` → `DaVinci_Resolve_21.1_Mac.dmg`)
- **Analyzed:** 2026-09-08
- **Source:** notarized installer, signed by Blackmagic Design Inc (Team ID `9ZGFBWLSYP`), timestamped 2026-09-07 — a one-day-old build.
- **Working tree:** `/tmp/resolve_211/` (DMG mounted at `/tmp/resolve_211_mnt`, all four payloads extracted, 16 GB total)
- **Compares against:** [`2026-09-07_21.0.4_findings.md`](2026-09-07_21.0.4_findings.md)

## TL;DR

**`Distribution` still omits `hostArchitectures`** — the spurious install-time Rosetta
prompt on Apple Silicon is **not fixed** in 21.1. That is five point releases
without a one-line attribute change.

But 21.1 is the first build in this tracked series to ship a *real* architecture
improvement. Two things genuinely got better:

- **`pg_dump` and `pg_restore` are now universal** (`x86_64 arm64`). They were
  Intel-only in both 21.0.0b and 21.0.4. This is the first time Blackmagic has
  actually rebuilt a shipped Intel-only binary as universal in the versions this
  repo has tracked.
- **The QuickLook generator was removed outright** from the RAW Player prereq,
  taking an embedded Intel-only copy of `BlackmagicRawAPI.framework` with it.

The Fairlight kext finding from 21.0.4 is **unchanged and still the worst thing in
the package**: the prereq is still stamped v1.1 and `CrystalDriver.kext` is still
x86_64-only.

## Distribution XML

The full options line, verbatim:

```xml
<options customize="allow" allow-external-scripts="no" rootVolumeOnly="true"/>
```

- **No `hostArchitectures` attribute** — unchanged from 21.0.0b and 21.0.4. False
  Rosetta prompt persists.
- Install gating is by OS version only (`pm_install_check` / `pm_volume_check`
  both require macOS 15.0+). Nothing in the Distribution references architecture
  at all.
- The two prereq stagers contain nested flat component pkgs with **no
  `Distribution`**, so they inherit whatever the postflight invoker decides.

## Intel-only inventory

### 1. `ManifestLite.pkg` — 23 files (was 25)

**Rosetta-relevant: 20**

Helper executables (`DaVinci Resolve.app/Contents/Applications/`):
- `EuphonixPanelDaemon`, `JLCooperPanelDaemon`, `TangentPanelDaemon`

> ✅ **`pg_dump` and `pg_restore` are no longer in this list.** Both now report
> `x86_64 arm64`. They were Intel-only in 21.0.0b and 21.0.4.

Codec dylibs (`DaVinci Resolve.app/Contents/Libraries/`) — 8, unchanged:
- `csehq2.dylib`, `csehqa.dylib`, `cseuvec.dylib` (Cineform HQ / HQA / UVec)
- `libgvcodec.dylib` (Grass Valley)
- `libsavce.dylib`, `libsavcehpp.dylib`, `libsavcempc.dylib`, `libsonyxavcenc.dylib` (Sony AVC / XAVC)

The same 8 dylibs mirrored under `Contents/XPCServices/IOXPC.xpc/Contents/Libraries/`,
plus the XPC binary itself:
- `IOXPC` — still entirely x86_64

**Inert on arm64: 3** (unchanged from 21.0.4)

| Intel-only file | Universal siblings in the same directory |
|---|---|
| `BlackmagicRawAPI.framework/…/Libraries/InstructionSetServicesAVX` | `DecoderMetal`, `DecoderOpenCL` |
| `BlackmagicRawAPI.framework/…/Libraries/InstructionSetServicesAVX2` | (same) |
| `Contents/Libraries/libArriImageSdkTransformsCpu_module.9.0.1.so` | `…CpuFma_module`, `…Metal_module`, `…OpenCl_module` |

x86-specific SIMD/scalar backends selected at runtime by instruction-set
dispatch. An x86_64-only dylib cannot be `dlopen`'d by an arm64 process at all,
so on Apple Silicon these are never loaded. Dead weight, not a Rosetta trigger.

**arm64-only (unchanged):** `Contents/Frameworks/libaf_arm64.framework/Versions/A/libaf_arm64`
— still the only arm64-only object in the entire installer.

### 2. `ManifestPanels.pkg` — 1 file (unchanged)

- `Library/Application Support/Blackmagic Design/DaVinci Resolve/Fairlight/iCan/System/libtcc.so.1.0`
  — Tiny C Compiler runtime, `Mach-O thin (x86_64)`, signed
  `com.blackmagic-design.fairlightpanels` (`9ZGFBWLSYP`).

This component ships exactly one Mach-O object, and it is Intel-only.

### 3. `blackmagic_raw_player_installer.tgz` prereq — 6 files (was 8)

44 Mach-O objects total (was 50). All 6 Intel-only files are the same
`InstructionSetServicesAVX` / `AVX2` pair, now repeated across **three** embedded
copies of `BlackmagicRawAPI.framework` rather than four:

- `Blackmagic RAW Player.app/Contents/Frameworks/`
- `Blackmagic RAW Speed Test.app/Contents/Frameworks/`
- `Blackmagic RAW Player.app/Contents/Library/Spotlight/BlackmagicRaw.mdimporter/Contents/Frameworks/`

> ✅ **The fourth copy is gone.** `Blackmagic RAW Player.app/Contents/Library/QuickLook/BlackmagicRaw.qlgenerator/`
> no longer exists — `Contents/Library/` now contains only `Spotlight`. The whole
> QuickLook generator was dropped, not just its Intel slice.

Same benign-on-ARM category. Everything else in this prereq is universal.

### 4. `fairlight_audio_accelerator.zip` prereq — 2 files, both Intel-only

**Unchanged from 21.0.4.** The staged archive still contains
`Fairlight Audio Accelerator v1.1.pkg` — same version string — and ships exactly
2 Mach-O objects, neither with an arm64 slice:

- `Applications/DaVinci Resolve/Uninstall Fairlight Audio Accelerator.app/Contents/MacOS/Uninstall Fairlight Audio Accelerator`
  — `Mach-O thin (x86_64)`, `com.blackmagic-design.CrystalDriver.uninstaller`. Will launch under Rosetta 2.
- `Library/Application Support/Blackmagic Design/Fairlight/Signed Extensions/CrystalDriver.kext/Contents/MacOS/CrystalDriver`
  — `Mach-O 64-bit kext bundle x86_64`, `com.blackmagic-design.driver.Crystal`,
  with `IOKitPersonalities`, signed `Developer ID Application: Blackmagic Design Inc (9ZGFBWLSYP)`.

🔴 **Still the real finding.** Rosetta 2 translates user-space processes only; it
does not translate kernel extensions. An Intel-only kext cannot load on Apple
Silicon, so the Fairlight Audio Accelerator card remains non-functional on ARM
Macs. Blackmagic would need an arm64 kext or, more likely, a DriverKit `.dext` —
**neither is present anywhere in the installer** (a search for `*.dext` across all
four components returns nothing, and `CrystalDriver.kext` is the only kext).

Postinstall path unchanged: `ManifestFairlightAudioAccelerator.pkg` runs
`postflight_fairlight_audio_accelerator.sh`, which shells out to the staged
`install_fairlight_audio_accelerator.sh`.

The one-line fix Blackmagic still has not shipped:

```xml
<options customize="allow" allow-external-scripts="no" rootVolumeOnly="true"
         hostArchitectures="x86_64,arm64"/>
```

The interesting shape of this release: Blackmagic clearly *did* do architecture
work on 21.1 — universalizing the PostgreSQL tools and dropping a stale QuickLook
plugin are both deliberate, targeted changes. They just did not touch the
installer manifest, which is the one change that would stop users seeing a
Rosetta prompt they do not need. The runtime picture improved; the install-time
picture did not move at all.

## Reproduction

```sh
mkdir -p /tmp/resolve_211 && cd /tmp/resolve_211
unzip -o ~/Downloads/DaVinci_Resolve_21.1_Mac.zip
hdiutil attach DaVinci_Resolve_21.1_Mac.dmg -nobrowse -mountpoint /tmp/resolve_211_mnt

pkgutil --check-signature "/tmp/resolve_211_mnt/Install Resolve 21.1.pkg"
pkgutil --expand "/tmp/resolve_211_mnt/Install Resolve 21.1.pkg" expanded
grep -i hostArchitectures expanded/Distribution || echo "NOT declared"

# Raw cpio payloads — note: NOT gzip (see guide recipe #021)
for p in ManifestLite ManifestPanels ManifestBlackmagicRawPlayer ManifestFairlightAudioAccelerator; do
  mkdir -p "expanded/$p.pkg/extracted"
  ( cd "expanded/$p.pkg/extracted" && cpio -id --quiet < ../Payload )
done

# Staged prereq archives (three levels down — see toolkit issue #2)
mkdir -p prereqs/rawplayer prereqs/fairlight
BASE="Library/Application Support/Blackmagic Design/DaVinci Resolve/Prereqs"
tar xf "expanded/ManifestBlackmagicRawPlayer.pkg/extracted/$BASE/blackmagic_raw_player_installer.tgz" -C prereqs/rawplayer
unzip -oq "expanded/ManifestFairlightAudioAccelerator.pkg/extracted/$BASE/fairlight_audio_accelerator.zip" -d prereqs/fairlight
pkgutil --expand prereqs/rawplayer/BlackmagicRaw_resolve.pkg rp_exp
pkgutil --expand "prereqs/fairlight/FairlightAudioAccelerator/Fairlight Audio Accelerator v1.1.pkg" fa_exp
for d in rp_exp fa_exp; do
  mkdir -p "$d/extracted" && ( cd "$d/extracted" && cpio -id --quiet < ../Payload )
done

# Intel-only sweep over any extracted tree
sweep() {
  find "$1" -type f | while read -r f; do
    file "$f" 2>/dev/null | grep -q Mach-O || continue
    A=$(lipo -archs "$f" 2>/dev/null)
    case " $A " in *arm64*) ;; *x86_64*) echo "${f#$1/}  [$A]" ;; esac
  done | sort
}
sweep expanded/ManifestLite.pkg/extracted
sweep expanded/ManifestPanels.pkg/extracted
sweep rp_exp/extracted
sweep fa_exp/extracted

# The kext, specifically
file "fa_exp/extracted/Library/Application Support/Blackmagic Design/Fairlight/Signed Extensions/CrystalDriver.kext/Contents/MacOS/CrystalDriver"
```

## Convention note: compare releases by path, not by count

Not a toolkit defect — a rule for writing these documents.

This release's Intel-only total fell 36 → 32 for two unrelated reasons:
`pg_dump` and `pg_restore` were **ported** (they moved from the Intel-only
bucket to universal), while `BlackmagicRaw.qlgenerator` was **deleted** (it left
the corpus entirely). Those mean opposite things — one is vendor progress, the
other is a dropped feature — yet both read as "-2" in a bare count.

`analyze_pkg.sh` already prints the full path list for each of its three
buckets, not just the totals, so diffing two runs' path lists tells the two
cases apart immediately. The ambiguity only appears if a write-up compares
integers. So: when comparing against a prior release, cite the files that moved
and say which way. The counts are a summary, never the evidence.
