# DaVinci Resolve 21.1 — macOS installer findings

- **Package:** `Install Resolve 21.1.pkg` (from `DaVinci_Resolve_21.1_Mac.zip` → `DaVinci_Resolve_21.1_Mac.dmg`)
- **Analyzed:** 2026-09-08
- **Source:** notarized installer, signed by Blackmagic Design Inc (Team ID `9ZGFBWLSYP`), timestamped 2026-09-07 — a one-day-old build.
- **Working tree:** `/tmp/resolve_211/` (DMG mounted at `/tmp/resolve_211_mnt`, all four payloads extracted, 16 GB total)
- **Compares against:** [`2026-09-07_21.0.4_findings.md`](2026-09-07_21.0.4_findings.md)

## TL;DR

**`Distribution` still omits `hostArchitectures`** — the spurious install-time Rosetta
prompt on Apple Silicon is **not fixed** in 21.1. That is five point releases
without a one-line attribute change.

But 21.1 is the first build in this tracked series to ship a *real* architecture
improvement. Two things genuinely got better:

- **`pg_dump` and `pg_restore` are now universal** (`x86_64 arm64`). They were
  Intel-only in both 21.0.0b and 21.0.4. This is the first time Blackmagic has
  actually rebuilt a shipped Intel-only binary as universal in the versions this
  repo has tracked.
- **The QuickLook generator was removed outright** from the RAW Player prereq,
  taking an embedded Intel-only copy of `BlackmagicRawAPI.framework` with it.

The Fairlight kext finding from 21.0.4 is **unchanged and still the worst thing in
the package**: the prereq is still stamped v1.1 and `CrystalDriver.kext` is still
x86_64-only.

**Update (2026-09-08): the prompt really is spurious, and this was proven by
installing.** Adding the one missing attribute and reinstalling puts 21.1 on an
Apple Silicon Mac with Rosetta 2 absent, running native arm64. Doing so also
surfaced two defects that static analysis alone had missed — a **fifth**
installer component (`ASAF_SDK.pkg`, Apple-signed) carrying the *same*
`hostArchitectures` defect despite a fully universal payload, and an
unconditional DolbyVision path bug. Both fail **silently**. See
[Installing without Rosetta 2](#installing-without-rosetta-2-2026-09-08).

four components returns nothing, and `CrystalDriver.kext` is the only kext).

`postflight_fairlight_audio_accelerator.sh`, which shells out to the staged
`install_fairlight_audio_accelerator.sh`.

## Installing without Rosetta 2 (2026-09-08)

The static analysis above says the Rosetta prompt is spurious. This section
records what happened when that was tested for real: **21.1 was installed and
run on an Apple Silicon Mac with Rosetta 2 absent, and it works.**

Host: M1, 16 GB, macOS 15.7.7 (24G720). Rosetta confirmed absent on five
independent signals — `/Library/Apple/usr` does not exist, no
`com.apple.pkg.RosettaUpdateAuto` receipt, nothing in `softwareupdate --history`,
and `launchctl print system/com.apple.oahd` reporting `active count = 0`.

> **Do not use `/usr/libexec/rosetta` as evidence.** It exists on every Apple
> Silicon Mac — `oahd`, `oahd-helper`, `runtime`, `translate_tool` — because
> Apple ships the daemon in the sealed read-only system volume. Every file is
> dated with the OS build. `softwareupdate --install-rosetta` installs the
> *translation runtime* to `/Library/Apple/usr/`, and that is the thing to test.

### The fix is one attribute

```sh
pkgutil --expand "Install Resolve 21.1.pkg" repack
# add hostArchitectures="x86_64,arm64" to <options> in repack/Distribution
pkgutil --flatten repack Resolve-21.1-arm64.pkg
installer -showChoiceChangesXML -pkg Resolve-21.1-arm64.pkg -target / > choices.xml
# set attributeSetting 0 for the choices you don't want
sudo installer -verbose -applyChoiceChangesXML choices.xml \
     -pkg Resolve-21.1-arm64.pkg -target /
```

Result: `The install was successful.` No Rosetta prompt, and `oahd` still at
`active count = 0` afterwards.

### Why the prompt happens at all

Blackmagic documents the mechanism themselves, in
`ManifestLite.pkg/Scripts/postflight.sh`:

```sh
# For some unknown reason this script runs in x86_64 mode even on Apple Silicon
# (can be verified with 'arch' command)
```

With no `hostArchitectures`, Installer runs the whole script phase translated.
`/bin/sh` is universal, so this is purely Installer policy — but with Rosetta
absent the translated script host cannot launch and the install dies.

Nothing else in the package needs Rosetta:

- **No Mach-O in any `Scripts/` directory** — all eight pre/postflight scripts
  across the four manifest components are `POSIX shell script text`.
- **Payload binaries are never executed**, only copied. The installer therefore
  does *not* crash on Intel-only content; it writes it out and moves on.
- **The `ddmx` branch is dead.** `postflight.sh` runs `${DMG_DIR}/.ddm/ddmx` if
  present — the only place an arbitrary binary would execute — and this DMG has
  no `.ddm` directory.

### The signature is not an obstacle

Re-flattening strips Blackmagic's signature. `/var/log/install.log` duly says:

```
External component packages (4) trustLevel=100 (trust evaluation failed:
  ... "The package "Resolve-21.1-arm64.pkg" is not signed.")
```

…and then installs it anyway. `sudo installer` performs no Gatekeeper or
notarization assessment, and a locally rebuilt file carries no
`com.apple.quarantine` xattr. The **app bundle's** signature is untouched by
this and still verifies after install (`valid on disk`, satisfies its Designated
Requirement) — only the outer installer wrapper is modified.

### Confirming native execution

Resolve's own log is the cleanest evidence:

```
Main      | INFO | Running DaVinci Resolve v21.1.0.0014 (macOS/Clang arm64)
GPUDetect | INFO |   - CPU: Apple M1, 8 threads, arm64
DDM       | INFO | DDM 1.4-a13 (macOS/arm64), DaVinci Resolve 21.1 build 14
```

> ⚠️ **`ps -o arch` does not work.** `arch` is not a valid `ps` keyword on macOS
> 15; it is silently dropped and the column never appears, which reads as a pass.
> Use the app's own log line above, or `launchctl print system/com.apple.oahd` —
> if `active count` is still `0`, nothing on the machine has been translated.

Runtime behaviour matched the static prediction:

| Prediction | Observed |
|---|---|
| Intel-only codec dylibs are inert, not Rosetta triggers (#034) | `IO codec library load completed in 303 ms`, no `dlopen` failure |
| `IOXPC.xpc` (x86_64-only) may not be reachable | never spawned at startup |
| Metal/GPU path unaffected | `resolve_graphics_log.txt`: `Error = 0, Fatal = 0, Warning = 0` |

### Defect 1 — `ASAF_SDK.pkg`: a nested false Rosetta prompt (Apple's)

The one thing that failed. `ManifestLite`'s postflight calls
`Prereqs/install.sh`, which untars `asaf.tgz` and runs
`installer -pkg ASAF_SDK.pkg`. That inner install refused:

```
./postflight.sh: +++ Installing ASAF
./postflight.sh: installer: This package requires Rosetta 2 to be installed.
./postflight.sh: installer: Error - ASAF SDK ... can't be installed on this computer.
./postflight.sh: !!! install failed
```

**All 10 of its Mach-O objects are universal (`x86_64 arm64`)** — nine ASAF Audio
Unit components plus `usr/local/lib/libASAF.dylib`. Nothing in it needs Rosetta.
It was refused solely because its `Distribution` reads:

```xml
<options customize="never" require-scripts="false"/>
```

This is the *same* defect as the parent, one level deeper — and it is not
Blackmagic's. The package is `com.Apple.pkg.ASAF.SDK`, signed by Apple and
notarized 2026-07-13; Apple built it. Apple also publishes the ASAF Production
Suite directly via the Apple Developer downloads portal, so the fix here is
probably to install Apple's own copy rather than to repackage a signed artifact.

**Status: parked** pending a decision on whether to report it to Apple and/or
install from the official source. Resolve runs fine without it; ASAF only
matters for Fairlight immersive/spatial audio.

### Defect 2 — DolbyVision: an unconditional Blackmagic bug

Also from the same postflight run:

```
cp:    //Library/Application Support/Blackmagic Design/DaVinci Resolve/DolbyVision/default_cm_config.bin: No such file or directory
chmod: //Library/Application Support/Blackmagic Design/DaVinci Resolve/DolbyVision/config.bin: No such file or directory
```

`postflight.sh` copies `DolbyVision/default_cm_config.bin` out of the *app
support* tree, but **no component in the installer ships a `DolbyVision`
directory**. The file exists only at
`DaVinci Resolve.app/Contents/Resources/default_cm_config.bin`. Verified by an
unrestricted `find` across all component payloads and both prereq archives.

This fails on every Mac, any architecture, any component selection — it has
nothing to do with Apple Silicon or with repackaging. It appears harmless in
practice: Resolve self-provisions a *user-level*
`~/Library/…/DaVinci Resolve/DolbyVision/config_v2.5.bin` on first run, so the
postflight copy looks like dead code aimed at a stale path. Reportable to
Blackmagic.

### Both failures are silent

`postflight.sh` does not `set -e` and never checks the exit status of the
prereq installer. The overall install reports success regardless. **Neither
defect above is visible in the installer's exit code** — both must be read out
of `/var/log/install.log`.

## ProRes RAW on Apple Silicon

Resolve's first run logs:

```
IO | ERROR | ProRes RAW SDK raw conversion plug-in loading error(s):
     unable to open default plug-in directory /Library/Application Support/ProApps/PlugIns/ProResRAW
```

**This is not a Blackmagic problem and not an architecture problem.** That
directory is created by Apple's free **Pro Video Formats** package
(<https://support.apple.com/en-us/106396>, ~10 MB, standalone — the download
route via Final Cut Pro's *Help → Download Additional Content* requires FCP
installed, which is not needed). Resolve simply reports the plug-in as missing
until it is installed.

Installed and verified on this machine (2026-09-09, arm64, Rosetta absent):

```
/Library/Application Support/ProApps/PlugIns/ProResRAW/AppleRawConversion.prrplugin
  Contents/MacOS/AppleRawConversion   x86_64 arm64
```

Universal, so **ProRes RAW works natively** and the error clears. The package
installed without a Rosetta prompt, so its `Distribution` does not carry the
`ASAF_SDK.pkg` defect.

### What it does and does not recover for Resolve

Installing it also drops codec bundles into
`/Library/Video/Professional Video Workflow Plug-Ins/`, which partly offsets
what Resolve's Intel-only `IOXPC` path costs. Only partly, and the split is not
intuitive — three of Apple's eleven bundles are **themselves Intel-only** and
cannot load into a native arm64 Resolve:

| Format | Resolve on arm64 | Provided by |
|---|---|---|
| ProRes RAW / RAW HQ | ✅ works | `AppleProResRAWCodec` (universal) |
| **XAVC-I** (Intra) decode | ✅ works | `AppleAVCIntraCodec` (universal) |
| **XAVC-L** (Long GOP) decode | ❌ | `AppleAVCLGCodec` — **`x86_64` only** |
| AVC-Intra encode | ❌ | `AppleAVCIntraEncoder` — **`x86_64` only** |
| XF-HEVC | ❌ | `AppleHEVCProCodec` — **`x86_64` only** |
| DNxHD / DNxHR decode | ✅ works | `DNXDecoder` (universal) |
| IMX, DVCPRO HD, Uncompressed, MXF | ✅ works | universal |
| CineForm, Grass Valley | ❌ | unaffected — Resolve's own Intel-only libs |

The XAVC line is the one to get right: **XAVC-I recovers, XAVC-L does not**,
because Sony's two flavours are handled by different Apple bundles with
different architecture support.

Note this is a *different* failure mode from the `hostArchitectures` defects
above. Those are manifest bugs — universal payloads refused over a missing
attribute, fixable in one line. These three bundles are genuinely un-ported
code. A codec bundle is `dlopen`'d into the host process, so an x86_64-only
bundle cannot load into a natively running Resolve at all, and **no attribute
fix or Rosetta install helps** short of running the whole application
translated.

> Caveat: the `.dmg` was not retained, so Apple's package was swept
> post-install from its receipt (`pkgutil --files com.apple.pkg.ProVideoFormats`)
> rather than analyzed beforehand. Analyze first next time.

## Which codecs are actually lost (runtime evidence)

The Intel-only inventory lists 8 codec dylibs and treats them alike. Exercising
the installed app shows **they are not alike**, and the sweep alone cannot tell
them apart. This is the clearest example in this document of static analysis
over-reporting.

### Resolve's codec menu is gated on encoder availability

The key observation. In Deliver → Render Settings on this machine:

| Format | Codec menu contains | Codec menu omits |
|---|---|---|
| QuickTime | Apple ProRes, APV, Avid DNxHD/HR, FFV1, **GoPro CineForm**, **Grass Valley**, H.264, H.265, Kakadu JPEG 2000, Photo JPEG, Uncompressed, VP9 | — |
| MXF OP1A | Avid 1:1, Avid DNxHD/HR, DNxUncompressed, H.264, H.265, Kakadu JPEG 2000, MPEG-2, XDCAM MPEG2 | **XAVC**, **AVC-Intra** |
| MXF OP-Atom | Avid 1:1, Avid DNxHD/HR, DNxUncompressed, Kakadu JPEG 2000, XDCAM MPEG2 | **XAVC**, **AVC-Intra** |

Resolve drops codecs whose encoder did not load. That makes the menu a usable
runtime probe — and it cuts both ways.

### Sony XAVC and AVC-Intra export: confirmed dead

Absent from the menu, and it is **not** an edition limitation. The main binary
carries the complete feature:

```
IOXavcEncoderWrapper
createSonyXAVCEncoder / destroySonyXAVCEncoder
"Failed to Initialise XAVC encoder (%d)" / "Failed to Encode XAVC"
SonyXAVC_10bit_LONG_100_3840x2160   (+ a full preset table, 178 XAVC strings)
AVC-Intra 100M 1080p25/50, AVC-Intra4K_444, AVC-Intra4K_HS, …
```

Those factory functions resolve into `libsonyxavcenc.dylib`, which exports
`sony_xavc_encoder::SonyXAVCEncoder::Initialise` / `EncodePicture` /
`GetEncodedPicture` — and is `x86_64` only. Resolve fully implements XAVC
export; the encoder simply cannot load, so the codec is never offered.

### CineForm and Grass Valley: probably *not* lost

Both are **present** in the QuickTime menu, in a menu that demonstrably filters
unavailable codecs. There is no universal `cse*` or `libgvcodec` anywhere in the
bundle — but `Contents/Libraries/libavcodec.60.dylib` is universal, and FFmpeg
implements CineForm as `cfhd`. The neighbouring menu entries (FFV1, VP9, Kakadu
JPEG 2000) are all classic libavcodec codecs, which is consistent with Resolve
exposing FFmpeg-backed encoders alongside vendor ones.

So the likely reading is that these four Intel-only dylibs are **redundant
legacy paths**, not lost functionality — the same category as the inert
instruction-set backends, arrived at for a different reason.

**Not yet confirmed by an actual render.** Menu presence plus a universal
backend is strong circumstantial evidence, not proof. A one-second export to
each would settle it.

### Consequence for the buckets

Recipe #034 splits Intel-only objects into "Rosetta-relevant" and "inert on
arm64" by looking for universal siblings *in the same directory*. That test does
not catch this case: the CineForm and Grass Valley dylibs have no siblings, yet
are plausibly still unused because an unrelated universal library provides the
same codec. A sweep cannot see that. **Only running the app can.**

The honest summary for this build on Apple Silicon:

| | Verdict | Basis |
|---|---|---|
| Sony XAVC export | ❌ dead | menu omission + Intel-only encoder + full feature in binary |
| AVC-Intra export | ❌ dead | same |
| XAVC-L decode | ❌ dead | Apple's `AppleAVCLGCodec` also Intel-only |
| CineForm | 🟡 probably fine | in a filtered menu; universal libavcodec present |
| Grass Valley | 🟡 probably fine | same |
| `IOXPC` | never spawned at startup | see [Confirming native execution](#confirming-native-execution) |

## Follow-ups for the toolkit

**One new, found by installing rather than by analyzing.** `analyze_pkg.sh`
stops one level too early: it handles prereq archives staged *by* a component
(`blackmagic_raw_player_installer.tgz`, `fairlight_audio_accelerator.zip`) but
does not recurse into an archive staged inside a payload's own `Prereqs/`
directory and invoked from a postflight script. `asaf.tgz` → `ASAF_SDK.pkg` sits
in exactly that blind spot, which is why the original sweep of this release
counted four components instead of five and missed a textbook
`hostArchitectures` mismatch — a fully universal payload refused on Apple
Silicon. The generalisation worth implementing: **any `installer -pkg` invoked
from a script is a component the sweep must follow**, wherever its archive lives.

This is also a reminder that a clean static verdict is not the same as a
successful install. The mismatch detector was right about the top-level package
and still missed a second, identical mismatch nested below it.

**A second limitation, from exercising the app rather than installing it.**
Recipe #034 separates "Rosetta-relevant" from "inert on arm64" by looking for
universal siblings *in the same directory*. That heuristic cannot see a codec
whose Intel-only vendor dylib is bypassed because an unrelated universal library
elsewhere in the bundle provides the same format — which is what appears to
happen with CineForm and Grass Valley versus `libavcodec.60.dylib`
([Which codecs are actually lost](#which-codecs-are-actually-lost-runtime-evidence)).
No static rule can settle that; only running the app can. This does not make
#034 wrong — over-reporting is the safe direction — but the toolkit should not
be read as producing a functional impact list. It produces a list of *candidates*.

Otherwise this analysis exercised the same paths that issues
[#2](https://github.com/AriESQ/macos-installer-info/issues/2),
[#3](https://github.com/AriESQ/macos-installer-info/issues/3) and
[#4](https://github.com/AriESQ/macos-installer-info/issues/4) covered — staged
prereq archives, kext classification, and instruction-set-dispatch false
positives — and the fixes merged in
[PR #6](https://github.com/AriESQ/macos-installer-info/pull/6) handle all three
correctly on this build.

## Convention note: compare releases by path, not by count

Not a toolkit defect — a rule for writing these documents.

This release's Intel-only total fell 36 → 32 for two unrelated reasons:
`pg_dump` and `pg_restore` were **ported** (they moved from the Intel-only
bucket to universal), while `BlackmagicRaw.qlgenerator` was **deleted** (it left
the corpus entirely). Those mean opposite things — one is vendor progress, the
other is a dropped feature — yet both read as "-2" in a bare count.

`analyze_pkg.sh` already prints the full path list for each of its three
buckets, not just the totals, so diffing two runs' path lists tells the two
cases apart immediately. The ambiguity only appears if a write-up compares
integers. So: when comparing against a prior release, cite the files that moved
and say which way. The counts are a summary, never the evidence.
