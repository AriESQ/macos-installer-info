# DaVinci Resolve 21.0.4 — macOS installer findings

- **Package:** `Install Resolve 21.0.4.pkg` (from `DaVinci_Resolve_21.0.4_Mac.zip` → `DaVinci_Resolve_21.0.4_Mac.dmg`)
- **Analyzed:** 2026-09-07
- **Source:** notarized installer, signed by Blackmagic Design Inc (Team ID `9ZGFBWLSYP`), timestamped 2026-08-03.
- **Working tree:** `/tmp/resolve_2104/` (DMG mounted at `/tmp/resolve_2104_mnt`, Lite payload extracted to `expanded/ManifestLite.pkg/extracted/`, 5.1 GB)
- **Compares against:** [`2026-05-23_21.0.0b_findings.md`](2026-05-23_21.0.0b_findings.md)

## TL;DR

Structurally unchanged from 21.0.0b. The main app is still universal, and **`Distribution` still omits `hostArchitectures`** — so the spurious install-time Rosetta prompt on Apple Silicon is **not fixed** in 21.0.4.

The runtime-Rosetta surface inside `DaVinci Resolve.app` is also unchanged: the same 22 Intel-only binaries. Three *new* x86_64-only files appeared, but all three are AVX/scalar SIMD backends that ship next to universal Metal/OpenCL siblings — they're inert on ARM, not new Rosetta triggers.

The genuinely new problem is in the **Fairlight Audio Accelerator** prereq, which was not swept in the 21.0.0b pass: its `CrystalDriver.kext` is **x86_64-only**. A kext cannot be translated by Rosetta, so that hardware is unusable on Apple Silicon, full stop.

## Package structure

Same 4-component bootstrapper as 21.0.0b. All Payloads still **raw cpio** (`ASCII cpio archive (pre-SVR4 or odc)`), not gzip.

## Intel-only inventory

### 1. `ManifestLite.pkg` — 25 files (was 22)

**The original 22, all unchanged from 21.0.0b:**

Helper executables (`DaVinci Resolve.app/Contents/Applications/`):
- `EuphonixPanelDaemon`, `JLCooperPanelDaemon`, `TangentPanelDaemon`
- `pg_dump`, `pg_restore`

Codec dylibs (`DaVinci Resolve.app/Contents/Libraries/`):
- `csehq2.dylib`, `csehqa.dylib`, `cseuvec.dylib` (Cineform HQ / HQA / UVec)
- `libgvcodec.dylib` (Grass Valley)
- `libsavce.dylib`, `libsavcehpp.dylib`, `libsavcempc.dylib`, `libsonyxavcenc.dylib` (Sony AVC / XAVC)

The same 8 dylibs mirrored under `Contents/XPCServices/IOXPC.xpc/Contents/Libraries/`, plus the XPC binary itself:
- `IOXPC` — still entirely x86_64

**3 new in 21.0.4 — benign on Apple Silicon:**

| New Intel-only file | Universal siblings in the same directory |
|---|---|
| `BlackmagicRawAPI.framework/…/Libraries/InstructionSetServicesAVX` | `DecoderMetal`, `DecoderOpenCL` |
| `BlackmagicRawAPI.framework/…/Libraries/InstructionSetServicesAVX2` | (same) |
| `Contents/Libraries/libArriImageSdkTransformsCpu_module.9.0.1.so` | `…CpuFma_module`, `…Metal_module`, `…OpenCl_module` (all `x86_64 arm64`) |

These are x86-specific SIMD/scalar backends selected at runtime by instruction-set dispatch. An x86_64-only dylib **cannot be `dlopen`'d by an arm64 process at all**, so on Apple Silicon they are never loaded — the universal Metal/OpenCL/NEON-FMA siblings are used instead. Dead weight on ARM, not a Rosetta trigger.

**arm64-only (unchanged):** `Contents/Frameworks/libaf_arm64.framework/Versions/A/libaf_arm64`

### 2. `ManifestPanels.pkg` — 1 file

- `Library/Application Support/Blackmagic Design/DaVinci Resolve/Fairlight/iCan/System/libtcc.so.1.0` — Tiny C Compiler runtime, `Mach-O thin (x86_64)`, signed `com.blackmagic-design.fairlightpanels`.

⚠️ Not necessarily new — the 21.0.0b sweep only covered the Lite payload, so this may have been present then and simply missed.

### 3. `blackmagic_raw_player_installer.tgz` prereq — 8 files

50 Mach-O objects total; 8 Intel-only, and all 8 are the same `InstructionSetServicesAVX` / `AVX2` pair repeated across **four embedded copies** of `BlackmagicRawAPI.framework`:

- `Blackmagic RAW Player.app/Contents/Frameworks/`
- `Blackmagic RAW Speed Test.app/Contents/Frameworks/`
- `Blackmagic RAW Player.app/Contents/Library/Spotlight/BlackmagicRaw.mdimporter/Contents/Frameworks/`
- `Blackmagic RAW Player.app/Contents/Library/QuickLook/BlackmagicRaw.qlgenerator/Contents/Frameworks/`

Same benign-on-ARM category as the in-app copies. Everything else in this prereq is universal.

### 4. `fairlight_audio_accelerator.zip` prereq — 2 files, and **both** are Intel-only

This component ships exactly 2 Mach-O objects and neither has an arm64 slice:

- `Applications/DaVinci Resolve/Uninstall Fairlight Audio Accelerator.app/Contents/MacOS/Uninstall Fairlight Audio Accelerator` — `Mach-O thin (x86_64)`, `com.blackmagic-design.CrystalDriver.uninstaller`. Will launch under Rosetta 2.
- `Library/Application Support/Blackmagic Design/Fairlight/Signed Extensions/CrystalDriver.kext/Contents/MacOS/CrystalDriver` — **x86_64-only kernel extension**, `com.blackmagic-design.driver.Crystal` v1.1, with `IOKitPersonalities`.

🔴 **The kext is the real finding.** Rosetta 2 translates user-space processes only; it does not translate kernel extensions. An Intel-only kext simply cannot load on Apple Silicon, so the Fairlight Audio Accelerator card is non-functional on ARM Macs with this build — and no amount of Rosetta will help. (Blackmagic would need to ship an arm64 kext or, more likely, a DriverKit `.dext`. Neither is present.)

Postinstall hooks: `Scripts/fairlight-preflight`, `Scripts/fairlight-postflight`.

## Reproduction

```sh
mkdir -p /tmp/resolve_2104 && cd /tmp/resolve_2104
unzip -o ~/Downloads/DaVinci_Resolve_21.0.4_Mac.zip
hdiutil attach DaVinci_Resolve_21.0.4_Mac.dmg -nobrowse -mountpoint /tmp/resolve_2104_mnt

pkgutil --check-signature "/tmp/resolve_2104_mnt/Install Resolve 21.0.4.pkg"
pkgutil --expand "/tmp/resolve_2104_mnt/Install Resolve 21.0.4.pkg" expanded
grep -i hostArchitectures expanded/Distribution || echo "NOT declared"

# Raw cpio payloads — note: NOT gzip (see guide recipe #021)
cd expanded/ManifestLite.pkg && mkdir -p extracted && cd extracted
cpio -id --quiet < ../Payload

# Intel-only sweep
find . -type f | while read -r f; do
  file "$f" 2>/dev/null | grep -q Mach-O || continue
  A=$(lipo -archs "$f" 2>/dev/null)
  case " $A " in *arm64*) ;; *x86_64*) echo "${f#./}  [$A]" ;; esac
done | sort

# Prereq stagers (skipped in the 21.0.0b pass)
tar xf ".../Prereqs/blackmagic_raw_player_installer.tgz" -C prereqs/rawplayer
unzip -o ".../Prereqs/fairlight_audio_accelerator.zip" -d prereqs/fairlight
pkgutil --expand prereqs/rawplayer/BlackmagicRaw_resolve.pkg rp_exp
pkgutil --expand "prereqs/fairlight/FairlightAudioAccelerator/Fairlight Audio Accelerator v1.1.pkg" fa_exp
# …then cpio-extract each Payload and re-run the sweep
```

## Follow-ups for the toolkit

1. **`analyze_pkg.sh` silently skips staged prereq archives.** ([#2](https://github.com/AriESQ/macos-installer-info/issues/2), bug) The Fairlight kext — the most severe finding here — lives inside a `.zip` inside a component Payload, three levels down. Worse than "not recursed": in the stub/downloader scan (`analyze_pkg.sh:214-216`), finding a staged `.tgz`/`.zip`/`.pkg`/`.dmg` sets `has_staged=true`, whose *only* effect is to suppress the stub warning at `:236`. The component then produces **no output at all** — it is neither flagged as a stager nor swept, and since the archive is never unpacked into `$ANALYSIS_DIR`, the arch sweep at `:315` can't see its contents either.
2. **Kexts/dexts deserve their own verdict line.** ([#3](https://github.com/AriESQ/macos-installer-info/issues/3)) An Intel-only `.kext` is categorically worse than an Intel-only dylib — Rosetta cannot rescue it. The summary currently lumps all Intel-only Mach-O together.
3. **Instruction-set-dispatch backends produce false positives.** ([#4](https://github.com/AriESQ/macos-installer-info/issues/4)) `InstructionSetServicesAVX`, `libArriImageSdkTransformsCpu_module`, etc. are x86-only *by design* and inert on ARM. Worth a heuristic: if an Intel-only dylib has a same-prefix sibling in the same directory that carries an arm64 slice, downgrade it from "Rosetta trigger" to "inert on ARM".
