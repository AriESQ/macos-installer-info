# Apple Pro Video Formats 3.1 — macOS codec package findings

- **Package:** `com.apple.pkg.ProVideoFormats`, version `3.1.1.1769503355`
- **Source:** <https://support.apple.com/en-us/106396> — free standalone download, ~10.2 MB, macOS 11.0.1+
- **Installed:** 2026-09-09 on Apple Silicon (M1, macOS 15.7.7) with **Rosetta 2 absent**
- **Related:** [`../davinci-resolve/2026-09-08_21.1_findings.md`](../davinci-resolve/2026-09-08_21.1_findings.md)

> ⚠️ **Scope caveat: this is a post-install sweep, not a pre-install analysis.**
> The `.dmg` was not retained, so the package's signature, `Distribution` and
> `hostArchitectures` declaration were never captured. Everything below is
> derived from `pkgutil --files` and `lipo` against what landed on disk. If this
> package is downloaded again, analyze it *before* installing — that is the whole
> point of this repo, and it was not done here.

## TL;DR

Installed to fix DaVinci Resolve's `unable to open default plug-in directory
/Library/Application Support/ProApps/PlugIns/ProResRAW` error. **It does fix
that**, natively.

But Apple ships **three Intel-only codec bundles** in a 2026 release. On Apple
Silicon they cannot load at all, so the formats they provide are simply
unavailable — and unlike a false Rosetta prompt, no attribute fix helps. These
binaries were never ported.

## `hostArchitectures` verdict

**Not directly observed** (see scope caveat). But it can be inferred: the package
installed successfully via `installer` on a machine with no Rosetta 2 runtime.
Had its `Distribution` omitted `hostArchitectures` the way `ASAF_SDK.pkg` does
(see the Resolve 21.1 findings), the install would have been refused outright
with *"This package requires Rosetta 2 to be installed."*

So this package does **not** carry the ASAF-class manifest defect. Its problem is
the opposite and more serious kind: **genuinely un-ported binaries**.

## Intel-only inventory — 5 objects across 3 bundles

All under `/Library/Video/Professional Video Workflow Plug-Ins/`:

| Object | Arch | Provides |
|---|---|---|
| `AppleAVCIntraEncoder.bundle/…/AppleAVCIntraEncoder` | `x86_64` | AVC-Intra **encode** |
| `AppleAVCLGCodec.bundle/…/AppleAVCLGCodec` | `x86_64` | AVC-LongG (incl. **XAVC-L**) |
| `AppleAVCLGCodec.bundle/…/mc_dec_avc.framework/Versions/11/mc_dec_avc` | `x86_64` | MainConcept AVC decoder |
| `AppleHEVCProCodec.bundle/…/AppleHEVCProCodec` | `x86_64` | XF-HEVC |
| `AppleHEVCProCodec.bundle/…/mc_dec_hevc.framework/Versions/11/mc_dec_hevc` | `x86_64` | MainConcept HEVC decoder |

The two `mc_dec_*` frameworks are MainConcept-licensed decoders. Their presence
suggests the blocker is a third-party licensing/porting dependency rather than
Apple's own code — but that is inference from the filename, not established.

**These are not Rosetta-recoverable in any useful sense.** A codec bundle is
`dlopen`'d into the host process; an x86_64-only bundle cannot be loaded by an
arm64 host at all. Installing Rosetta 2 would not make these work in a natively
running DaVinci Resolve — it would only help if the *entire host application*
were run translated.

## Effect on DaVinci Resolve 21.1

The reason this package was installed. Net effect on the Resolve install
documented in the companion findings:

| Format | Before | After |
|---|---|---|
| ProRes RAW / RAW HQ | ❌ plug-in dir missing | ✅ native |
| XAVC-**I** (Intra) decode | ❌ Resolve's own `libsonyxavcenc` etc. are Intel-only | ✅ via `AppleAVCIntraCodec` |
| XAVC-**L** (Long GOP) decode | ❌ | ❌ `AppleAVCLGCodec` is Intel-only |
| AVC-Intra encode | ❌ | ❌ `AppleAVCIntraEncoder` is Intel-only |
| XF-HEVC | ❌ | ❌ `AppleHEVCProCodec` is Intel-only |
| DNxHD / DNxHR decode | ❌ | ✅ via `DNXDecoder` |
| IMX / DVCPRO HD / Uncompressed / MXF | ❌ | ✅ |
| CineForm, Grass Valley | ❌ Resolve's libs Intel-only | ❌ unaffected by this package |

The XAVC split is the subtle one and easy to get wrong: **XAVC-I recovers,
XAVC-L does not**, because Sony's two XAVC flavours are handled by different
Apple bundles with different architecture support.

## Reproduction

Post-install sweep, no installer required:

```sh
pkgutil --pkg-info com.apple.pkg.ProVideoFormats

# every Mach-O the package placed, with arch
pkgutil --files com.apple.pkg.ProVideoFormats --only-files | while read -r rel; do
    f="/$rel"
    file "$f" 2>/dev/null | grep -q Mach-O || continue
    printf '%s  [%s]\n' "$rel" "$(lipo -archs "$f" 2>/dev/null)"
done

# just the unusable ones
pkgutil --files com.apple.pkg.ProVideoFormats --only-files | while read -r rel; do
    f="/$rel"
    file "$f" 2>/dev/null | grep -q Mach-O || continue
    A=$(lipo -archs "$f" 2>/dev/null)
    case " $A " in *arm64*) ;; *) echo "INTEL-ONLY: $rel [$A]" ;; esac
done
```

## Follow-ups for the toolkit

**A gap worth considering: `analyze_pkg.sh` has no post-install mode.** Every
recipe assumes an installer you still have. Once a package is installed and the
`.dmg` discarded, the receipt database (`pkgutil --pkg-info` / `--files`) is
still a complete, authoritative file list — enough to run the same Intel-only
sweep and produce the same three-bucket verdict, as this document demonstrates.
A `--receipt <pkg-id>` mode would let the toolkit audit software already on a
machine, which is the common real-world case and currently unsupported.

Note also that the **inert-vs-relevant distinction from recipe #034 does not
apply here**. Resolve's Intel-only files were mostly instruction-set dispatch
backends with universal siblings. These three bundles have no siblings — each is
the sole implementation of its format. They belong in the "genuinely
unavailable" bucket, not the inert one.
